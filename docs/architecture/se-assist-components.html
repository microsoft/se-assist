Reading guide, exact agent/model/action contracts, source index and design notes

Read from inbound data to processing, storage and UI. Each storage letter identifies one logical domain. UI badges name a feature's primary read set, including the shared panels explicitly listed on its card. The green rails connect each domain to the UI groups that consume it. Use the storage selector to isolate one domain; use 100% for legible agent tables.

This is a functional data view, not a deployment or process diagram. Application-mediated access is abstracted away; the runtime view owns the execution and trust boundaries. A UI-to-storage relationship does not grant renderer access to SQLite, credentials, files or remote services. Not every page mounts at once, and most AI actions run on demand rather than as part of ingestion.

Agent and model interpretation

  • All 23 catalog agents appear inside their invoking UI or data component. Python alias and weak-link utilities are separately identified as two non-catalog helpers. Components without an agent say so; deterministic joins, dates, validation, calculations and rendering have no LLM model.
  • Primary and Utility are model-selection contracts, not invented fixed model IDs. The Utility role resolves to the explicit Utility selection/configuration, or to Primary when no separate model is configured. A model error never triggers a different model. Only Secretary Search Scope and Secretary pin gpt-5.6-luna with high reasoning.
  • Work Agent, Work Outputs, influence analysis, ingestion AI and the two Secretary agents are Copilot-only. Connected Copilot failures do not switch to Foundry. For other eligible features, Foundry is considered only when Copilot is disconnected and Foundry is fully configured; both role labels use its configured deployment.
  • Agent lists include direct actions and explicitly embedded Workloads, Agenda, MeetingDetailPanel or milestone DetailCard actions. Navigating to another feature does not transfer that feature's agent ownership. The catalogue index below preserves exact IDs, roles, explicit reasoning and source files.
  • Secretary's UI is currently hidden. Work Agent is registered behind its investigation interface but has no current page caller; it is not presented as an active Deep Research control.
  • Only Work Agent has a model-selected tool loop: workiq_search, workiq_read_email, workiq_read, workiq_document, web_search and web_read. These six functions are read-only, with a 12-round bound. Other catalog tool names describe deterministic grounding, not extra MCP servers or permission grants.
  • Work Outputs research/gap steps call read adapters through application-controlled orchestration. They are not a second unrestricted tool-loop agent. Ingestion's desktop-resolved Utility selection is passed into Python; a legacy Python default is not a fixed desktop model.

Reads, live results and source modifications

  • Dynamics API reads and mutations are drawn twice to distinguish operations on the same connection. WorkIQ is similarly repeated for batch ingestion, live reads and the explicit mailbox draft action; these are not separate deployments.
  • HTTP POST is not necessarily a write: Power BI querydata/DAX, enterprise search, availability and meeting-time queries retrieve data. WorkIQ's do_action transport can carry a read query or an actual mutation; classify it by action semantics.
  • Dynamics POST/PATCH changes require an explicit user action, preserve opportunity-before-milestone gating and mirror successful changes locally. AI agents propose content; the application validates and executes the chosen operation.
  • Work Outputs' Outlook action creates a threaded createReplyAll draft through WorkIQ MCP. It does not send email. A generated reply saved in W is not itself an Outlook mailbox write; creating the Outlook draft is a separate action.
  • ACR has durable SQLite row caches/snapshots. Foundry usage has a 15-minute identity-scoped memory cache; capacity queries have a 60-minute identity-aware memory cache. Neither is a durable copy of usage/capacity rows in SQLite.
  • Directory reads use WorkIQ Graph fetch and write through to org_people in the local database. Live documents, original email, schedules, public pages and Seismic results are not all batch-ingested. Fetched meeting transcripts are saved with meeting work; selected research evidence/outputs can be saved independently.
  • Seismic uses an authenticated persistent browser session, not MCP and not a fabricated app REST API. Public search uses Copilot's read-only web MCP; publisher pages use direct HTTPS without user cookies or credentials.
  • The inference API is separated from external source modification. Bounded grounding leaves the device for inference, but model calls are not CRM or mailbox writes. Opening an external link is also not a write.

Design notes

3200 x 2880 reference poster, deliberately larger than the two 1920 x 1080 presentation views. The user's requested workflow replaces the former orchestration-centred component map: inbound reads, ordered processing, explicit storage domains, UI read sets, then separate outbound execution. No process/orchestration box is included. The overview and runtime views remain complementary, unchanged perspectives.

The architecture-diagram template's flat node geometry, common-region zones, orthogonal single-ended SVG connectors, semantic rails and three type sizes (28 / 16 / 12) are retained. Repeated connections distinguish operation semantics, not extra services. Storage dependency rails are keyed logical references, not a universal integration bus. Full per-component agent/model/action tables are visible rather than relegated to hover text.

The six UI groups preserve 21 routed surfaces and three shared visualization cards. All model calls use the existing shared scheduler, including desktop-launched Python helpers.
