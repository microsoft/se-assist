Process ownership, identity and action contracts, source anchors and design notes

Use this view to explain execution and data trust. Shaded process/context regions describe ownership; source-category cards are groupings, not new intermediary services. Main-process agents, tool implementations, adapters and domain services are enclosed together. Local files, SQLite and transient state are separate from that execution boundary.

Renderer and preload boundaries

  • desktop\main.js creates the outer BrowserWindow with shell-preload.js, context isolation enabled and Node integration disabled. shell.html hosts the application in a webview.
  • The embedded application guest uses se-assist-preload.js, not the shell preload. Its isolated preload exposes seAssistAPI; React-side electronBridge.js wraps invoke calls and progress events.
  • React owns presentation and transient UI state, including CRM sync coordination. Privileged requests cross IPC; app React code does not directly open SQLite, read credentials or launch subprocesses. The shell preload only exposes a version property.

Privileged execution and account scope

  • Main registers feature IPC and owns external clients, credentials, persistence, agent execution and child-process lifecycle. Payload and active-account checks happen there; a renderer-facing SQL path also applies connection-local account-write protection.
  • The saved User Home TPIDs are the active roster. Reads use active_* views; account work holds roster leases. Archiving changes membership, not durable user history. This is portfolio scope, not a replacement for upstream authorization.
  • The catalog has 23 local agent specifications. Only Work Agent has a model-selected loop: four read-only WorkIQ functions and two public-web functions. Other catalog grounding inputs and Work Outputs source orchestration are deterministic application code.
  • Local Tasks, workloads, notes, links and saved outputs are validated application writes. CRM mutations and Outlook reply-all draft creation are explicit application actions, not research-tool capabilities; no email-send action is provided.

Identity, remote inference and subprocesses

  • Microsoft/Power BI and GitHub identity caches use OS-encrypted safeStorage, not SQLite token tables. WorkIQ maintains its own M365 identity/cache. Seismic OIDC remains in its isolated persistent Electron browser context.
  • All model work enters the shared scheduler. Desktop-launched Python AI holds an external scheduler slot for its subprocess duration. The model provider card represents clients, not a local model server.
  • Connected Copilot is an explicit provider choice. A connected-provider failure does not switch to Foundry; Foundry is eligible only when Copilot is disconnected, configuration is complete and the feature permits it. Work Agent, Work Outputs/research, influence analysis and ingestion AI are Copilot-only.
  • WorkIQ is a tracked local MCP subprocess over stdio JSON-RPC. The application stages selected M365 JSON, launches Python, then normalizes, redacts, links and upserts into the same seassist.db used by main. Staging is transient, not a second durable data store.
  • Local-first does not mean local-only inference. Bounded grounding leaves the device for remote models; public queries are scrubbed and direct publisher reads omit user cookies/credentials.

Persistence versus caches

SQLite contains synced CRM/M365 evidence, durable authored work and ACR row caches. Backup/report/dossier files and encrypted credential caches are local files, not database rows. Foundry Deep-Dives usage is a 15-minute identity-scoped memory cache and is not written to SQLite. Live directory, document and original-email reads are not all ingested.
